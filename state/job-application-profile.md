## LOW COMPETITION - weight this as heavily as fit

Faisal's explicit priority. A good match with 15 applicants beats a perfect match with
400.

**Where the applicant count is published** (LinkedIn, some Greenhouse boards): sort
ascending. Under 25 is a strong buy. Over 100, skip unless the fit is exceptional.

**Where it is not published, use these proxies:**
- Role on the company's OWN board (Ashby, Greenhouse, Lever, Workable) and NOT
  cross-posted to LinkedIn or Indeed. Strongest signal by far.
- Posted hours ago rather than days.
- Specific stack requirements, e.g. "React Native plus Expo plus AWS", which filter out
  far more applicants than a generic "Full Stack Engineer".
- Company with no press coverage and no recognisable name.
- Unusual titles: "Product Engineer", "Founding Engineer", "First Engineer" get searched
  far less than "Software Engineer".

Score each job 0-100 on fit and 0-100 on low-competition. Rank by the two combined,
weighted evenly. Report both numbers so Faisal can see the trade.

**Do not invent an applicant count.** If it is not published, say "not published" and
score on the proxies. A fabricated number would send him at the wrong jobs.

### Compiling to PDF — without this, Stage 2 cannot apply

A packet holding LaTeX source is not enough. Stage 2 has to UPLOAD A FILE. On 7 August,
10 CVs were prepared and only 1 was ever compiled.

`\documentclass{resume}` is a CUSTOM class and is NOT in any TeX distribution. The class
file is stored at `claude/cv-resume-class.md`. For each job:

1. `mkdir -p /mnt/user-data/outputs`  — **this exact directory, and no other**
2. Write `resume.cls` from `claude/cv-resume-class.md` into it, verbatim
3. Write the tailored `<company-slug>.tex`
4. Run `pdflatex -interaction=nonstopmode <company-slug>.tex` twice
5. Assert the PDF exists and is exactly ONE page. Two pages means drop a project and
   recompile. A compile error means fix it, never ship a broken CV.
6. Record in the packet **that it compiled and how many pages** — not the path.

**Why `/mnt/user-data/outputs` and nowhere else.** The browser's `file_upload` tool only
accepts files from the session's outputs or uploads folders, or a folder the user has
connected. A PDF sitting in `/home/claude/anything` is rejected outright. Verified by
test on 12 August: a PDF in `/mnt/user-data/outputs` attached to a live form correctly.

**And the PDF does NOT survive to Stage 2.** Stage 1 and Stage 2 run in different
sessions with different containers. The file compiled at 9 AM is gone by the time Stage 2
starts. So compiling here is a VALIDATION step — it proves the LaTeX is correct and fits
one page, catching errors while there is still time to fix them. **Stage 2 recompiles
from the LaTeX carried in the packet.** That is why the packet must contain the full
LaTeX source, not a file path.

If pdflatex is unavailable, say so loudly at the top of the report.

## Timing evidence

Applying within 24 hours gets 14.2% response versus 7.3% after seven days. The first
four days is up to 8x more likely to interview, decaying about 28% per day. Remote
software roles pull 300 to 800 applications in 24 hours, so speed matters more than
polish. Best window is Tuesday to Thursday, 8 to 10 AM in the company's timezone.

## Known reality check, 7 August 2026

The 7 August run screened 300+ postings across six sweeps and delivered **10 jobs, not
20**. The binding constraint was not freshness and not remote status. It is that almost
every remote engineering role is locked to a country list that excludes Pakistan.

That is the honest shape of this market. A run that delivers 10 real jobs is doing well.
A run that delivers 20 by relaxing the filters is wasting his mornings on applications
that were never going to be read. Deliver the honest number and say why.
